## 1. 它是什么 / 解决什么问题

**一句话**：rag-search 是个人 AI 助手（Hermes）的一个 RAG 检索插件——把用户的 Obsidian 知识库变成 agent 可检索的外部知识，回答问题时只把**高置信的相关笔记块**注入上下文，并给出处。

**解决什么问题**：
- LLM 上下文窗口有限，个人知识库（81 篇笔记、717 个块）不可能全塞进去
- 每次提问实时检索最相关的片段 → 模型基于**用户自己的笔记**回答（而不是凭空编造）
- 关键约束：**宁缺毋滥**——检索结果不可靠时不注入，让 agent 自己判断（绝不喂错误上下文误导模型）

**使用场景**：agent 对话中用户问"RRF 融合原理是什么"→ 插件从 llm-wiki 检索相关笔记块 → 注入 → 模型结合笔记回答并标注来源。

📌 **一句话**："我做了一个 RAG 检索插件：把个人知识库变成 agent 可检索的外部记忆，混合检索 + 置信度守卫，只注入高置信的笔记块，检索不靠谱时宁可不注入。"

## 2. 整体架构

```
┌─ 工具层  tools.py ──────────────────────────────┐
│  rag_search 工具（agent 可调用，可传 top_k）       │
└──────────────┬──────────────────────────────────┘
               │ 调用
┌──────────────▼──────────────────────────────────┐
│  引擎层  vaultrag/__init__.py                    │
│  engine.search()  ← 单一事实源（唯一检索入口）      │
│  查询 → 长度门槛 → 混合检索 → 过滤 → rerank → guard │
└──────┬───────────────────┬──────────────────────┘
       │                   │
┌──────▼──────┐    ┌───────▼──────┐
│ 数据层      │    │ 评测层        │
│ retriever.py│    │ evals/       │
│ (索引/检索) │    │ 93 golden     │
│ embedding.py│    │ cases + L1-L4 │
└─────────────┘    └──────────────┘
```

**一次查询的旅程**（数据流）：
```
"RRF 融合原理是什么"
 → 长度门槛（≥2 字符）
 → 混合检索：BM25（中文 bigram，本地）+ bge-m3 向量（云端）各取 top-48
 → 块级 RRF 融合（k=60）→ 8 候选（每笔记取最优块；index/log/SCHEMA 在索引构建时已排除）
 → cross-encoder rerank（bge-reranker-v2-m3）对前 8 候选打分
 → guard 三档：top1 < 0.02 incorrect / 0.02~0.60 ambiguous / ≥0.60 correct
 → correct → 注入 top-8 块 × 每块 600 字符（带来源标注）
```

📌 **一句话**："架构分四层：工具层（agent 入口）、引擎层（单一检索入口 search()）、数据层（索引/向量/排序）、评测层（93 条 golden cases 四层验证）。所有调用方共用同一个 search()，杜绝逻辑漂移。"

## 3. 核心技术原理

### 3.1 混合检索（BM25 + 向量）
- **BM25 字面匹配**：中文 bigram 分词（纯 numpy 本地实现），擅长精确词面匹配（"MoA"、"RAG"这类术语、代码符号）
- **bge-m3 向量语义匹配**（云端 API）：理解语义相似（"上下文压缩和消息角色交替有什么联系"这类换说法的问题）
- 互补：BM25 抓词面、向量抓语义，单独用都有盲区

### 3.2 块级 RRF 融合
- **RRF（Reciprocal Rank Fusion）**：对两个排序结果按 `Σ 1/(k + rank)` 融合，k=60（论文标准值）——不依赖分数可比性（BM25 分数和向量相似度量纲不同，不能直接相加）
- **块级**：融合键是 (笔记, 块) 而不是笔记——修复了"笔记对了、块错了"的经典问题（原实现按笔记融合后取末位块）
- **每笔记取最优块**（max_chunks_per_note=1）：保证注入的 8 块来自 8 篇不同笔记（multi-hop 问题的关键）

### 3.3 cross-encoder rerank 精排
- 两阶段检索的经典结构（arXiv 2604.01733：混合检索比单方法 recall +15-30%；cross-encoder 两阶段 rerank 再提升 nDCG@10 最高 28%）
- 召回阶段（BM25+向量）是"粗筛"，rerank 对候选逐对细读打分——分数比向量相似度可靠得多
- **双重职责**：既给 guard 提供置信分数（门槛判定），又按分数重排 hits（排序）

### 3.4 guard 三档守卫（CRAG 思想 + 保守化）
- 借鉴 CRAG 论文（arXiv 2401.15884）三档评估思想：
  - **Correct**（top1 ≥ 0.60）→ 注入
  - **Ambiguous**（0.02~0.60）→ 不注入（CRAG 原设计是检索+web search 混合，我们没有 web search 环节，所以保守化：不注入，把纠错交给 agent 弹性）
  - **Incorrect**（< 0.02）→ 拦截
- 0.02 保留价值：trace 里失败模式分类（明确无关 vs 低置信）+ 未来做降级注入/补充检索的现成分界线
- **查询级判定，不是块级**：guard 只看 top1（最高分块 ≥0.60 → 整个查询判 correct），一旦正确就注入前 8 块——**第 2-8 块不要求分数**（可能只有 0.04/0.006）。块级取舍不是引擎的事，是 agent 的事（注入完整候选让它自己挑）——CRAG 的 Correct 也是"至少一个文档达标→整批使用"，区别是 CRAG 有 decompose 精炼环节，我们把精炼职责交给 LLM

> 💬 **一句话**："guard 是查询级守卫：top1 ≥ 0.60 判这个查询有答案（correct），然后注入前 8 块——块级过滤不是引擎的事，是 agent 的事（注入完整候选让它自己挑）。CRAG 的 Correct 也是'至少一个文档达标'→ 整批使用，区别是 CRAG 有 decompose 精炼环节，我们把精炼职责交给了 LLM。"

### 3.5 面包屑+标签（消融验证 2026-08-30）

块结构 = **面包屑**（`笔记路径 > H1 > H2`）+ 正文 + **`[tags: ...]`**（frontmatter 分类）。消融（有 vs 无，93 条评测集实测）：

| 优点 | 数据 |
|---|---|
| **召回零损失** | 相关块 top-8 覆盖 94% vs 94%（完全相同） |
| **负样本更安全** | rerank top1 max 0.39 vs 0.50（0.60 线余量 0.21 vs 0.10）——面包屑/tags 稀释偶然词面匹配（正则化效果，实测意外发现） |
| **语义覆盖显著更好** | L4 Recall **0.977 vs 0.912**（+6.5pp，DeepEval 判定）——面包屑/tags 让块文本更完整（章节归属+分类信号），裁判判"上下文覆盖答案"的通过率更高；Precision 持平（0.930 vs 0.931） |
| **语义锚点** | 模型直接看到"这段属于哪篇笔记哪个章节"——跨笔记同名词不混淆 |
| **分类信号** | tags 补语义分类（检索/面试回答可引用） |
| **零成本** | 块数相同（717），只是文本前后缀 |

结论：保留——召回无损失、负样本更稳、模型可读性更好，无任何代价。

> 💬 **一句话**："面包屑和标签我做过消融：召回覆盖率 94% vs 94% 完全相同——它们不影响检索质量；但负样本 rerank 分数上限从 0.50 降到 0.39——面包屑/tags 稀释了偶然词面匹配，对守卫有正则化效果。而且模型能直接看到'这段属于哪篇笔记的哪个章节'。零成本、双收益，所以保留。"

### 3.6 注入设计
- 块按标题切分（≤1600 字符，超长按段落二次切），注入截断 600 字符/块
- 注入格式：`<knowledge_context>` 独立 user 消息 + 来源标注——**不碰 system、不改历史**（prompt cache 契约：缓存前缀稳定，注入放独立消息不破坏缓存）

📌 **一句话**："技术栈是教科书两阶段检索：BM25 补词面、向量补语义、RRF 块级融合、cross-encoder 精排、CRAG 式三档守卫。每个技术都有论文出处或实测依据。"

## 5. 架构设计考量

1. **单一事实源**：`engine.search()` 是唯一检索入口——工具、评测、未来任何调用方共用。曾经有两份复刻逻辑（工具 handler + context engine）导致行为漂移，重构后消灭
2. **fail-open**：任何失败（无 key/索引异常/网络断连）→ 返回 None/skipped，**绝不打断对话**——检索是增强不是依赖
3. **引擎不做 LLM 该做的事**：不做查询改写/缩写展开（消融实验证明无收益）——缩写理解是 LLM 的能力，引擎只做检索
4. **插件化自包含**：索引/检索/守卫/评测全在插件内，不依赖 Hermes 核心——可独立测试、独立演进
5. **缓存契约**：注入放独立 user 消息，不碰 system、不改历史——长对话 prompt cache 不失效（成本关键）
6. **可审计**：每次检索写结构化 trace（query/verdict/分数/原因）——出问题可逐条回放

📌 **一句话**："设计上六个考量：单一事实源、fail-open、职责边界（引擎不做 LLM 的事）、插件自包含、prompt cache 契约、全链路 trace 可审计。"

## 6. 评测与指标

### 6.1 评测体系
- **93 条 golden cases**（查询 + 期望笔记 + AI 生成的简洁标准答案）：single 32 / multi 34 / abbreviation 12 / negative 15
- **四层评测**（各答一个问题）：
  - **hit@1 / Recall@k**（字面命中，严格尺）：返回笔记是否命中期望笔记（内部编号 L1）
  - **FPR / precision**（生产口径）：真实 search 路径跑全量（注入判定 + 无关拦截，内部编号 L2）
  - **ROC / operating point**（注入线敏感性）：0.20-0.80 网格扫描（误杀/误放曲线，内部编号 L3）
  - **Contextual Precision / Recall**（语义判定，宽松尺）：DeepEval + DeepSeek v4-flash 裁判（内部编号 L4）
  > 注：L1-L4 是内部协议编号，面试/对外讲用业界指标名（hit@k / FPR / ROC / Contextual P-R）

### 6.2 指标结果（当前代码实测 2026-08-30）

| 指标（业界名） | 值 |
|---|---|
| hit@1（单篇） | **94%（30/32）** |
| 完全命中（跨篇） | 82%（28/34） |
| hit@1（缩写） | 50%（6/12） |
| FPR（无关拦截） | **0 误放**（15/15） |
| Contextual Precision（语义排序） | **0.93** |
| Contextual Recall（语义覆盖） | **0.98** |

### 6.3 修复史（为什么从差到好）
修复前（真实块口径）：Contextual Precision 0.52 / Recall 0.68——两个确定性 bug：
1. **块选择缺陷**（by_source last-wins）：正确笔记却返回该笔记最不相关的块（占 L4 失败 67%）
2. **排序缺陷**：rerank 只当门槛不排序，相关块被无关块挤到 rank 3-5

三项代码修正（零调参、零改测试数据）：
```
① 块级 RRF 融合（每笔记取最优块）   ② rerank 全量重排   ③ 注入策略对齐 CRAG（低置信不注入）
Contextual P/R: 0.52/0.68 → 0.93/0.98
```

### 6.4 性能（实测）
- 单次查询：热 3.4~4.7s（rerank 云端打分为主；打分 8 项落地后最差 13s 场景消失）
- 混合检索本地 0.02s；索引加载 7.4s（首调）
- 全量评测 93 条 **~2 分钟/次**（35s×3，候选 8 + 打分 8 后提速 20 倍），3 次运行结果一致（确定性）

📌 **一句话**："评测用 93 条真实库内 golden cases 四层验证：hit@1 94%、无关 0 误放、Contextual Recall 0.98。最有说服力的故事是修复史：两个确定性 bug（块选错、不排序）导致 Contextual P/R 只有 0.52/0.68，我用三项代码修正拉到 0.93/0.98——全程没调一个阈值。"

## 7. 运行实例（真实 trace，2026-08-30 实测）

查询：「**RRF 融合原理是什么**」——完整跑一遍生产路径，看每一步实际发生什么。

### 7.1 候选池（混合检索 → 块级 RRF 融合，8 块，展示前 5）

| 排名 | RRF 分 | 来源笔记 |
|---|---|---|
| 1 | 0.0269 | `concepts/rag-retrieval-pipeline.md` |
| 2 | 0.0245 | `hermes-interview/hermes-vaultrag-interview.md` |
| 3 | 0.0202 | `concepts/cross-encoder.md` |
| 4 | 0.0196 | `hermes-interview/vaultrag-positioning-and-evolution.md` |
| 5 | 0.0193 | `concepts/moa-mixture-of-agents.md` |

### 7.2 guard rerank 打分（cross-encoder 对前 8 候选精排）

| 分数 | 来源笔记 | 解读 |
|---|---|---|
| **0.922** | `concepts/rag-retrieval-pipeline.md` | 正确答案块——**断层式领先** |
| 0.041 | `vaultrag-positioning-and-evolution.md` | 相关但非直接答案 |
| 0.039 | `hermes-vaultrag-interview.md` | 面试笔记（提及 RRF） |
| 0.006 | `concepts/cross-encoder.md` | 弱相关 |
| 0.000 | `concepts/moa-mixture-of-agents.md` | 无关（RRF 融合召回但被压分） |

**看点**：RRF 召回阶段是"粗筛"（5 个候选分数 0.019~0.027，差距小）；**rerank 精排把正确答案块拉到 0.922**——分数从"都差不多"变成"断层式区分"，这就是两阶段结构的意义。

### 7.3 guard 判定与注入

```
top1 = 0.922 ≥ 0.60（correct 档）→ 注入 top-8 块
top2 = 0.040 → margin = 0.882（明显领先）
```

注入 8 块（全部 ≤600 字符，无截断）：
`rag-retrieval-pipeline` → `vaultrag-positioning-and-evolution` → `hermes-vaultrag-interview` → `cross-encoder` → `hermes-moa-context-injection` → `moa-mixture-of-agents` → `hermes-request-assembly-extras` → `kwargs`

### 7.4 注入文本示例（第 1 块，358 字符完整）

```text
RAG 检索管线（混合检索 + RRF + rerank + guard） > 各环节技术拆解 > 3. RRF
### 3. RRF（Reciprocal Rank Fusion，倒数排名融合）

**是什么**：把多个检索结果的排名融合成一个。公式 Σ 1/(rank + k)，k=60。

- 不关心绝对分数（BM25 和向量分数的量纲不同，不能直接加权），只看排名
- 每个文档在"BM25 排名"和"向量排名"里各算一次倒数，相加排序
- 出处：滑铁卢大学 + Google 2019
[tags: ai, rag, retrieval, bm25, embedding, rrf, hybrid-search, concept]
```

**看点**：块自带「面包屑 → 标题 → 定义 → 要点」结构——模型看到前两行就知道这块讲什么；来源标注让回答可引用。
